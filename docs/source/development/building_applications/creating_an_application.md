# Creating a ManiVault-based application

A ManiVault-based application is a deliberately composed distribution of the ManiVault core, selected plugins, application-specific configuration, and optional curated content. The application can range from a general analysis environment to a focused viewer designed for one dataset or workflow.

The recommended development path is:

1. Define the intended user experience.
2. Compose the core and plugins with DevBundle.
3. Build and verify the integrated application.
4. Create stable application identity and branding.
5. Configure the start page and supplied content.
6. Validate the complete application as an end user.

This page connects those stages. The linked guides provide the detailed procedures for each customization or content mechanism.

## Understand the application layers

Treat the application as three related but independent layers:

| Layer | Defines | Primary mechanism |
|---|---|---|
| Build composition | Which executable, plugins, and binary dependencies are present | DevBundle and CMake |
| Runtime customization | Identity, settings namespace, branding, splash screen, and start-page layout | `Customization/app.json` and assets |
| Curated content | Projects and tutorials offered to users | Published projects and project/tutorial DSNs |

This distinction prevents a common design mistake: hiding a plugin in the interface does not remove it from the distribution, and adding a project to a catalog does not install the plugins that project requires. The build must contain the required capabilities before configuration or content can expose them.

## 1. Define the application before selecting plugins

Write down the application contract from the user's perspective:

- What data formats can users open?
- Which analyses or transformations can they run?
- Which views should be available?
- Is the application exploratory, or should it open into a controlled workflow?
- Can users create arbitrary plugin instances?
- Does the application work offline, or can it retrieve projects and tutorials?
- Which platforms and hardware configurations must be supported?

Translate each required capability into a plugin repository. At minimum, a usable application normally needs a way to load its intended data and at least one way to inspect or visualize it. For example, the DevBundle `basic` configuration combines the core, CSV loader, and scatterplot plugin.

Avoid adding every available plugin without considering the product. A smaller, intentional plugin set reduces startup work, dependency surface, interface complexity, and the combinations that need release testing.

## 2. Create an application-specific DevBundle

Use {doc}`DevBundle <../building_manivault/dev_bundle>` as the authoritative build environment. DevBundle keeps the selected repository revisions together, resolves their configured prebuilt binaries, and generates one umbrella CMake project.

Start by copying DevBundle's current `config.json` to an application-owned configuration file. Add a named bundle under `build_bundles`; do not edit the shared default configuration as the long-term source for an application.

```json
{
  "name": "my_viewer",
  "build_dir": "my_viewer",
  "mv_repos": [
    { "repo": "core", "branch": "master" },
    { "repo": "CsvLoader", "branch": "master" },
    { "repo": "Scatterplot", "branch": "master" },
    {
      "repo": "MyViewerPlugin",
      "branch": "main",
      "local": "D:/Projects/MyViewerPlugin"
    }
  ]
}
```

This is a `build_bundles` entry, not a complete DevBundle configuration file. Retain and update the accompanying `repo_info` and `prebuilt_binaries` sections. Add your plugin to `repo_info` when DevBundle needs to know about its subprojects or prebuilt binary dependencies.

Create the environment:

```console
python makeproject.py use --cfg_file D:/Projects/my-viewer/devbundle.json my_viewer --cmake
```

DevBundle will create isolated `source`, `build`, and `install` trees for `my_viewer`, obtain the configured platform binaries, and open the generated project in CMake GUI. Repositories marked with `local` remain external working checkouts and are added to the umbrella build without being cloned.

### Pin what constitutes a release

Moving `master` or `main` branches are convenient during active development, but they do not describe a reproducible released application. Before releasing, record the exact core and plugin revisions that were tested. DevBundle accepts a `tag` in place of a branch, so release tags or dedicated release branches are preferable to moving development branches.

The important property is that another developer can reconstruct the same combination of core, plugins, and binary packages later.

## 3. Build the integrated application

Configure the generated umbrella project and build `MV_Application`. For a release build generated by DevBundle:

```console
cmake --build my_viewer/build --target MV_Application --config Release --parallel
```

Run the application from:

```text
my_viewer/install/Release
```

Building the umbrella project ensures that the core and selected plugins use the same compiler, Qt package, architecture, ManiVault installation, and build configuration. It also allows CMake to respect the dependency order described by DevBundle.

Before branding the application, verify the composition itself:

- the application starts without missing-library or plugin-load errors;
- each intended plugin appears and can create an instance where appropriate;
- intended data formats can be loaded;
- a minimal representative workflow completes;
- plugins excluded from the application are not required by that workflow;
- Debug and Release artifacts have not been mixed.

Resolve composition and compatibility failures here. Runtime customization should not be used to conceal a broken build.

## 4. Establish application identity

Open the customization interface with **Ctrl+F8** and configure the application identity. The complete procedure is described in {doc}`app_customization`.

Set these values early:

- organization name;
- organization domain;
- full application name;
- base/display name and version policy.

These values are not merely cosmetic. Qt uses the organization and application identity to locate persistent settings. Changing them after users adopt the application can make existing preferences appear to disappear because the application starts reading a different settings namespace.

After saving, the core writes the configuration to:

```text
Customization/app.json
```

Keep the resulting file under version control with the application definition. Treat UI-based editing as a convenient authoring mechanism and the saved file as the deployable artifact.

## 5. Add visual branding

Use the customization interface to set the logo, in-application icon, About text, and start-page appearance. Keep the distinction between application UI assets and platform packaging assets:

- the configured icon affects ManiVault's windows and interface;
- it does not automatically replace the icon embedded in a Windows executable or macOS application bundle;
- platform executable icons belong to the later packaging process.

For a custom startup experience, add:

```text
Customization/assets/SplashScreen.html
```

The {doc}`splash_screen_customization` guide documents supported placeholders, the custom-assets URL scheme, Content Security Policy, and progress bridge. Preserve progress and error presentation unless the application intentionally replaces that feedback with an equivalent mechanism.

## 6. Design the start page

The start page is the application's main product-level entry point. Configure it around the workflows you actually support rather than enabling every available section.

Possible sections include:

- opening and creating projects;
- recent projects;
- project catalogs;
- creating a project from data;
- creating from a workspace template;
- tutorials.

An expert analysis tool may favor recent projects and compact presentation. A focused viewer may instead emphasize one curated project catalog and a small set of tutorials. Configuration is stored in `app.json`.

Do not expose an entry point until its complete path works. For example, showing a project catalog is useful only when its metadata is reachable and the application contains every plugin required by the offered projects.

## 7. Choose how users receive projects

Normal and published projects serve different purposes:

| Project form | Use it when |
|---|---|
| Normal project | Users should continue editing the analysis and workspace |
| Published project | The application should present a controlled, reproducible layout and restrict what users can add |

Use {doc}`publishing_a_project` to prepare a controlled project. Publishing can fix the view layout and restrict which additional plugins users may create through the interface. It does not install plugins; every plugin already used by the published project must be included in the application build.

Projects can then be made discoverable through a project DSN. The application's `Customization/projects.json` can list project data sources, while a plugin can register its own source through its factory. See {doc}`hosting_projects` for the metadata schema, compatibility fields, hosting requirements, and registration API.

For each project offered by the application, verify:

- its `requiredPlugins` metadata matches the actual plugin metadata;
- its core version is compatible with the application;
- its download URL is direct and available under the intended network policy;
- its layout works at supported display sizes;
- its data volume fits the advertised hardware requirements;
- unavailable content produces an acceptable user experience.

## 8. Add onboarding content

Tutorials can explain the intended workflow and optionally open an accompanying project. The {doc}`hosting_tutorials` guide describes tutorial JSON, hosting, tags, version requirements, and factory registration.

Use tutorials to teach application tasks, not merely individual controls. A useful onboarding sequence normally covers:

1. what the application is for;
2. how to open the supplied or user-owned data;
3. the primary analysis or viewing workflow;
4. how to interpret and export the result;
5. where to obtain support or further documentation.

If a tutorial references a project, test the tutorial and project as one versioned unit. Both must remain compatible with the core and plugin set in the application.

## 9. Organize the application sources

Keep the product definition outside generated DevBundle directories. One practical repository layout is:

```text
my-viewer/
├── README.md
├── devbundle.json                 application bundle definition
├── Customization/
│   ├── app.json
│   ├── projects.json              optional project data sources
│   └── assets/
│       ├── SplashScreen.html
│       └── branding assets
├── content/
│   ├── projects.json              remotely hosted catalog source
│   └── tutorials.json             remotely hosted tutorial source
└── release/
    ├── release-notes.md
    └── verification-checklist.md
```

The exact layout is an application-team choice. The important distinction is between maintained source artifacts and generated `build` or `install` output. During development, copy or install the maintained `Customization` directory next to the built application. A packaging process should automate that step for releases.

Do not edit the copy inside a generated install directory as the only source of truth; recreating the bundle or installation can discard it.

## 10. Validate from an end-user environment

Before treating the application as complete, test the assembled experience rather than its components in isolation.

### Build and startup

- Reconstruct the environment from the recorded DevBundle configuration.
- Build from a clean build tree.
- Start the installed application without developer-only environment variables.
- Confirm that all intended plugins load and no unintended plugin is present.

### Identity and persistence

- Verify application name, organization, icon, logo, splash screen, and About text.
- Restart the application and confirm settings persist in the intended namespace.
- Upgrade from the previous application version and check whether settings should be retained.

### Projects and tutorials

- Open every bundled or advertised project.
- Test published-project restrictions from an end-user account.
- Test remote content online, offline, and with an unreachable endpoint.
- Confirm version and required-plugin filtering behaves as intended.

### Representative workflows

- Run the smallest supported dataset through the primary workflow.
- Exercise a realistically large dataset on minimum supported hardware.
- Verify cancellation, progress, and error reporting for long operations.
- Confirm application-specific documentation and support links are reachable.

## Iterating safely

When only the application configuration or assets change, rebuild or recopy those artifacts as required by the development setup. When repository membership, order, local paths, or dependency declarations change, regenerate DevBundle's umbrella project:

```console
python makeproject.py use --cfg_file D:/Projects/my-viewer/devbundle.json my_viewer --mode cmake_only
```

When core or plugin versions change, perform the composition checks again before evaluating branding or content. Project metadata and tutorials may also need new compatibility information.

## What this workflow does not yet cover

At this point you have a reproducible application build and its maintained runtime configuration. Creating an installer or portable distribution adds a separate set of concerns: deploying Qt runtime libraries, selecting plugin artifacts, embedding platform icons, including licenses, signing, clean-machine validation, and defining an update strategy. Those belong to the packaging and deployment stage.
